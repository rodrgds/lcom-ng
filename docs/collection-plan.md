# Student game collection workflow

Done means a reusable collection manifest lists as many verified recent student games as the corpus and an additional GitHub search yield, starting from 30 imported public projects; each has pinned provenance, its original source and assets, a valid lcom.json mobile profile and an actual game-derived icon. A responsive web grid and a fullscreen three-column native Android grid launch them, returns reliably to the menu, and works in desktop browsers. Every included game must build on both targets and receive a recorded representative gameplay/input check. Original game code stays unchanged except separately documented, verified upstream defects.

1. Recover the previous corpus, pin/import 30 playable games into examples/community, and record source hashes and upstream license/attribution. Keep workers isolated under build/collection-workers and integrate reviewed snapshots only.
2. Establish a small collection manifest consisting of project folder paths. Resolve each project through the existing lcom.json owner; centralize collection metadata and build routing in sdk/collection.
3. Build native Android collection packaging first around a native launcher Activity, one shared compilation of runtime objects and one game library per project. Run games in a separate Android process, preserving the standalone export contract and reliable menu return.
4. Build a responsive web launcher from the same manifest, with separate game documents and an obvious return to games. Desktop browsers use the same web build.
5. Import in two disjoint batches of 15. Configure controls from source and observed input. Reuse actual student art for icons. Preserve all original C, headers, Makefiles and assets; record any confirmed source-defect patch separately.
6. Verify manifest validation and relocation, source provenance, every game's web/native build, representative input/gameplay, native process return, real mobile layouts, keyboard/focus behavior and browser errors. Record unsupported projects honestly and replace rejected candidates until all viable selected candidates are verified; reject incomplete projects and exact mirrors explicitly.
7. Produce the collection APK and web folder, write a teacher-facing guide and run the repository's verification gate. Do not publish or commit without a request. Keep physical-device performance separate from emulator evidence.

Rigor: high, because one package combines many independent student projects and the preceding native linker defect showed why menus alone are insufficient. Canonical decisions: docs/collection-decisions.tsv. Per-game evidence: examples/community/catalog.json and reproducible verification scripts, with large logs/screenshots under build/collection-qa.
