# Minixsweeper

## Goal and Application
Our goal was to implement a version of the world-famous game *Minesweeper* in the special LCOM Minix 3 environment. In this game, a map is generated with bombs placed at random positions and the player must use logical reasoning to uncover all tiles without detonating any bombs.

We successfully implemented the traditional *Minesweeper* gameplay. Additionally, we implemented a *Hint* feature accessible through a button. The player has the choice to use the hint once in each game and it reveals a single non-bomb tile. Beyond the classic mode, we also implemented a new game mode called *“deceiver”*. In this mode, the map can mislead the player, this means that numbers displayed on the board may not always be accurate, making purely logical decisions unreliable.

As expected for any game, there are different difficulty levels: easy, medium and hard. Each difficulty influences the size of the map and the number of bombs placed on it. On *“easy”* the map is 8x8 and it has 10 bombs. On *“medium”* we the map is slightly bigger, it is 12x12 with 25 bombs. Lastly, on *“hard”* the map is 16x16 and has 50 bombs on it.

## Structure

For our project we divided the structure into two bigger scenarios: the hardware interface and the software architecture. For the first, we reused the implementation of low level functions that handles each I/O device developed during the semester. Additionally, we utilized the MVC (Model - View - Controller) for the architecture of our game since we were already familiar with it.

![Architecture Diagram](/doc/report/out/architecture/architecture.svg)

Considering MVC pattern, the model contains the game logic, map logic, auxiliary data structures (in *gametypes.h*) and our main menu implementation. The view is responsible for displaying the data from the model, this means that the view does not handle any logic, only handles rendering tasks. Lastly, the controller handles the user inputs (and device interrupts) and translates it into actions.

The *proj.c* contains the setup of *LCF* (LCOM Framework) and the game setup inside *proj_main_loop*. Each of these files contains the low level functions we developed and headers with macros that simulates controllers during the semester: *kbc.c/h, mouse.c/h, graphics.c/h, utils.c, timer.c, rtc.c/h, i8042.h, i8254.h* and *VBE.h*.

The *game.c* contains logic for initiating the game and ending the game. *Map.c* contains the functions related to the map, like creating it, placing bombs in normal mode and deceiver mode, freeing the memory allocated for the map, etc.

The *view.c* handles the drawing of all elements’ sprites that were generated by functions defined in *sprite.c*.

The *controller.c* acts between the game and the hardware. In other words, it wraps low level functions that (un)subscribe to I/O devices and handles the interrupts generated by those devices and translates to game logic what that data means. For example, during the game the controller captures the right-click mouse button and asks *map.c* to handle the flag logic.

## Devices
Our game utilizes the following I/O devices: the *mouse*, the *timer* and the *graphics card*. We incorporated the *Real Time Clock* (RTC) too.

### Mouse
The mouse is used for menu navigation, that is, choosing the game mode, selecting the difficulty, starting a match and closing the game itself. Once a match is started, the mouse is used for playing the game. With the left mouse button the player is able to uncover a map tile and with the right mouse button the player places (or removes if there is already a flag) a flag, indicating a suspected bomb. The mouse also handles returning to the main menu when a match ends - whether through victory or defeat. Additionally, players can cancel an ongoing match at any time by clicking the icon in the top-right corner of the screen.

### Timer
Our game utilizes the timer in two distinct ways. Primarily, it supports the graphics card by maintaining the frame rate, as is standard in most graphical applications. Additionally, we employed the timer as a crucial part of our game’s logic. Specifically, we used the *timer_ticks* as the seed for *srand()* function calls, ensuring proper randomization during map generation. This approach guarantees unique and unpredictable map configurations for each match played.

### Video Card
The video card handles all visual rendering in our game. In our game, the video card uses the 0x115 mode with 800x600 resolution, direct color mode and 16.8M colors (24 bits per pixel (8:8:8)).

To avoid any visual artifacts in our game we utilized the double buffer technique. In each timer interrupt, the back buffer is cleaned, then all the game elements are drawn into the back buffer. Only after the frame is fully rendered, the back buffer content is copied to the front buffer. Also, considering our chosen display is relatively small, *memcpy* command is fast enough to give the user a seamless experience.

For the game's visual design, we employed XPM images that were either created in-house or sourced from royalty-free online repositories. These XPM files were then converted into sprite formats compatible with our rendering system, enabling seamless integration and display within the game environment.

### Real Time Clock
The RTC serves as our game's timing mechanism, precisely tracking and displaying elapsed match duration. We managed to do that by capturing the timestamp of when the match began, then comparing with the current time after every 30 rendered frames and calculating the delta to update the displayed time. With this approach we were able to maintain accurate timing while optimizing performance by avoiding a lot of RTC queries.

## Differentiating Features
We believe that our project stands out through both technical decisions and innovative gameplay design. The implementation of the Model-View-Controller architectural pattern creates an optimized environment for current development and for future expansion of game features, like a leaderboard, new game modes, etc.

Also, we consider that the most innovative feature we have in our project is the *deceiver* mode that is not common in Minesweeper games that already exists across the internet. In addition to that, we consider that our attention to details makes the project even more special. For example, we dynamically place the bombs on the map so that the first tile reveal never detonates a bomb and also gives some safe space for the player. Also, we would like to highlight the menu responsiveness with the hover effect details. Last but not least, we have dedicated our efforts to maintain equilibrium between challenge and enjoyment, so that the player does not get really frustrated, but still wants to play the game.
